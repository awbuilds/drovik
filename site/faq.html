Product & architecture

What it is.

What is Drovik?

A self-hosted, agentless web workspace for Linux servers. It puts saved SSH hosts, a full terminal, SFTP files, host health, processes, systemd services, logs, Docker and host diagnostics, snippets, local users and audit history in one browser interface. The browser talks only to the Drovik backend; the backend talks to your hosts over SSH and SFTP.

Does it install an agent on the managed host?

No. Drovik uses the OpenSSH server and SFTP subsystem already present on the host. There is no daemon, package, scheduled task or persistent helper. If the host lacks a tool a panel needs, the panel reports that capability as unavailable.

Does it need root?

No. Drovik acts as the SSH user you configure and never silently escalates. Remote permissions remain authoritative: if the account cannot read a file, restart a service or use Docker, the operation fails visibly. A Drovik administrator is still a privileged role for the servers assigned to that account.

Which hosts are supported?

Linux is the full-feature target: the validated matrix includes Ubuntu Server 22.04/24.04 LTS, Debian 12, Rocky Linux 9, AlmaLinux 9 and Fedora Server 40+. Other current Linux distributions with the required tools are expected to work. macOS and BSD get read-only monitoring (host, load, memory, filesystems, network and uptime); Linux-only panels are unavailable there. Windows is not supported. The controller needs Linux amd64 or arm64.

What does a host need?

OpenSSH 7.4+ or compatible; Linux with /proc; the SFTP subsystem for Files; systemd 230+ with systemctl for Services; journalctl with JSON output for Logs; and ps with -eo for Processes. Missing pieces are reported individually, and the rest of the workspace keeps working.

Does it support Docker and Kubernetes?

Docker, yes — through the host's Docker CLI over SSH, never a mounted socket. You can inspect containers and images, view logs and inspect data, and start, stop, restart or remove a container by a validated ID. These actions are potentially root-equivalent, so they require confirmation, are audited and are blocked for read-only assignments. Drovik is not a Compose or Kubernetes manager.

Can it change disks, firewall, network, packages or cron?

Packages and Drovik-managed cron entries are supported with validation, confirmation and audit. Disk, network and firewall changes are opt-in: they stay disabled until the operator sets DROVIK_ENABLE_DESTRUCTIVE_HOST_OPS=true, and then require an administrator, CSRF, explicit confirmation and audit. Format and partition require typing the exact device; protected mountpoints and mounted devices are refused. These commands can still destroy data or cut off the host, so test on a disposable target.

Does it keep metric history and raise alerts?

Yes, within limits. Drovik retains local metric samples for a configurable window (24 hours by default) with a hard sample cap, draws history charts and evaluates in-app threshold rules. A rule can also deliver an encrypted webhook; there is no email, chat or pager integration and no long-term time-series platform. Treat it as a local operational aid, not an enterprise monitoring system.

Security & data

What it can see.

How are SSH credentials stored?

Encrypted at rest with AES-256-GCM, using a random nonce and associated data that binds the ciphertext to the record. The 32-byte key comes from the environment or a mounted file and is never stored in SQLite, the repository or the image. Credentials are decrypted only immediately before an SSH connection and are never returned to the browser after submission.

What happens if I lose the encryption key?

Stored SSH credentials cannot be recovered. The database and the key are one backup boundary. Back up both, keep the key separate from the database copy, and never commit the key. A backup without the key is not a complete Drovik backup.

Is there any telemetry?

No. No analytics, advertising, crash reporting or vendor cloud. Drovik does not send usage data or diagnostics to the project. The service stores what it needs for your instance locally, and the only network connections it makes are to the servers you configure.

Does it verify SSH host keys?

Strictly. The first connection shows the fingerprint for explicit approval. A later key mismatch blocks the connection with no insecure fallback and no silent continue. Host keys are stored per server with approval metadata.

Can several people use one instance?

Yes. Administrators create local accounts with administrator, operator or read-only roles and assign per-server read or write access; at least one administrator must remain. Local TOTP MFA is available. Optional OIDC sign-in links to a pre-existing local account and never auto-provisions users. HashiCorp Vault KV v2 can supply SSH credentials without storing the secret in Drovik.

What can a read-only user actually do?

Inspect the servers assigned to them. The backend blocks a PTY, file mutations, process, service, Docker and destructive host actions, snippet execution and alert changes. The menu hiding a button is not the control; the server-side authorization check is.

Where does my data live?

On the machine running Drovik, in local SQLite and the data directory. That includes account metadata, sessions, server records, encrypted credentials, host keys, audit events, snippets, assignments, configurable metric samples and alert rules. File contents, terminal input/output and log contents are not retained by default. Your backups are your responsibility.

Does this website use cookies or analytics?

No. This site is static HTML, CSS and JavaScript. It sets no cookies, runs no analytics and loads no third-party resources. A theme preference is stored in your browser's localStorage and never leaves it. A hosting provider may keep standard request logs under its own policy; the project does not receive or analyze them. The Drovik application itself uses a session cookie for login.

Operations & limits

What it takes to run.

How do I install and upgrade it?

The primary path is Docker Compose behind a TLS reverse proxy; release archives and a systemd unit template are also provided. Back up the database and encryption key first. Migrations run before the service accepts traffic and are forward-only. After an upgrade, verify /readyz and the version in Settings. A failed migration is a failed upgrade: restore the backup.

What are the known limitations?

Linux is the full-feature target; macOS/BSD are read-only monitoring and Windows is unsupported. Destructive disk/network/firewall actions are opt-in and can still destroy data or cut off a host. Identity is local or OIDC, and alerting stops at webhooks. There are no resumable transfers or background transfer jobs and no systemd unit-file editing. SQLite allows one writer, so use local storage and stop Drovik for cold backups. Real-host validation is bounded by the documented matrix and automated fixtures.

Which browsers are supported?

Current Chrome, Firefox, Safari and Edge with ES2022, WebSocket and ResizeObserver support. The workspace is not designed for legacy browsers or embedded webviews with restricted storage and WebSocket behavior.

Is v1.3.1 production-ready?

It is the current stable line: the Phase 9 advanced-management release plus a security patch after a second source-first audit. The first audit of v1.0.0 fixed five findings in v1.0.1; the second audit of the Phase 9 tree fixed seven findings in v1.3.1. It is volunteer-maintained and carries the documented limits above. Treat it as one more privileged tool: put it behind TLS, restrict who can reach it, use a strong administrator password and test your backups.

What happens when a host is missing a tool?

The affected panel shows an explicit unavailable state with a stable error code. It does not fake empty data, fall back to an unsafe command or retry forever. The compatibility page lists the expected tools for each feature.

Project & license

How it is maintained.

Is it free?

The software is free software under the GNU Affero General Public License v3.0 only. There is no paid tier, hosted upsell or feature held back behind a purchase. The AGPL applies to the code: if you run a modified version as a network service, you must offer its corresponding source.

Does the project run a hosted Drovik service?

No. Drovik is self-hosted software. The maintainers do not operate instances for users and cannot see or recover your database, credentials or audit history. This website is static; the application you run is yours.

Can I contribute?

Yes. Read CONTRIBUTING.md and the repository's AGENTS.md contract, then open a focused branch and pull request. main is protected: work goes through review, required checks and conversation resolution. Security-sensitive changes get explicit review.

How do I report a bug or a security issue?

For a bug, open a GitHub issue with the version, environment, a minimal reproduction and the stable error code. Never include secrets or real hostnames. For a vulnerability, use the repository's private Security, then Advisories, then Report a vulnerability flow. Do not open a public issue for a security problem.

Is the name final?

Drovik is a working name pending trademark clearance. The license grants rights to the code, not to the project's name or marks.

What support is available?

This is a volunteer-maintained open-source project with no guaranteed response time. Security reports are prioritised; general issues are handled as capacity allows. The project cannot recover credentials without your key, manage hosts without SSH access or provide private deployment consulting.

Still stuck? Start with the documentation index, then open an issue with the exact version, host distribution, tool versions and stable error code. Do not paste credentials, private keys, terminal output or production logs.
