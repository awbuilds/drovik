Features

Every room in the workspace.

Drovik is not a dashboard bolted onto a shell. It is one workspace with a shared server context, a real terminal, verified state and an audit trail that stays on your instance.

The shape of a session

Add a host. Open one room. Act with receipts.

The interface follows the work: trust the host first, keep the context visible, then make every change answer to the remote result.

01

Add a host and review its key

Save the address, user and authentication method. On the first connection, Drovik shows the host-key fingerprint for explicit approval. A changed key later blocks the connection.

02

Work inside one server context

Terminal, files, health, operations and audit share the same selected host. The context stays visible, so a dangerous action cannot quietly land on the wrong machine.

03

Act with a result you can inspect

State-changing actions are confirmed and audited. Where the host can be re-read, the panel shows the new state instead of assuming the request worked.

Servers

Trust starts before the first command.

Save a host once, then choose password or private-key authentication. Drovik tests the connection and detects what the host can actually do. The first connection requires an explicit host-key decision.

  • Strict host keys. Unknown fingerprints are shown for review; a changed key blocks the connection with no insecure fallback.
  • Credentials stay server-side. They are encrypted at rest and never returned to the browser after submission.
  • Egress policy. Loopback, link-local, multicast, unspecified and cloud metadata addresses are denied by default; private ranges are configurable for homelabs.
  • Capability-aware. Missing tools become stable error codes, not silent empty panels.

Terminal

A real PTY, not a command runner.

The terminal is a first-class tool, not an escape hatch. It runs over an authenticated WebSocket, handles resize, copy and paste, and closes cleanly when the session or the user leaves.

  • xterm.js on the client. A familiar terminal surface, with the server context visible around it.
  • Bounded sessions. Per-user and global limits, rate limits, message size limits and origin checks.
  • Clean lifecycle. Sessions close on unmount, logout, revocation, expiry, server switch and shutdown.
  • Nothing retained. Terminal input and output are not written to Drovik's database by default.

Files

Files without the FTP client.

Browse a directory, stream a transfer, edit a bounded text file and create, rename or delete an entry. Paths are resolved and checked in the backend before the SFTP operation runs.

  • Traversal and symlink checks. A path that escapes the allowed root is rejected, not normalized into something surprising.
  • Streamed transfers. Uploads are written to a private staging file, then the final mode is applied before an atomic rename.
  • Bounded editing. The text editor has a hard size limit; a stale file is reported instead of overwriting a newer version silently.
  • Recursive-delete guards. Destructive file operations require confirmation and stay within the intended path.

Health, history & alerts

Agentless health, with a memory.

CPU, load, memory, filesystems, network counters and uptime come from /proc on Linux and portable tools on macOS/BSD. Drovik keeps configurable local samples and evaluates in-app threshold alerts — not a hosted monitoring platform.

  • Two-sample rates. CPU and network deltas appear on the second sample; the first is honestly marked as a baseline.
  • Missing is missing. An unavailable collector is reported individually; the rest of the overview still renders.
  • Bounded local history. A configurable retention window, 24 hours by default, with a hard sample cap.
  • Alerts stay local by default. Threshold rules are evaluated in the app. An optional encrypted webhook can notify one external endpoint; there is no email, chat or pager integration.
  • Read-only non-Linux. macOS and BSD report host, load, memory, filesystems, network and uptime; Linux-only panels are labelled unavailable.

Processes & services

Act on what the host confirms.

Inspect processes and signal a PID you own, with an identity check before the signal. Discover systemd units and run enumerated actions; after an action, Drovik re-reads the unit state instead of assuming it worked.

  • Enumerated signals. SIGTERM and SIGKILL only, after a PID identity check. No arbitrary signal strings.
  • No hidden elevation. Actions run as the SSH account; a permission failure is a visible failure.
  • State re-reads. systemd actions show the state the host reports after the request.
  • No unit editing. Activation and inspection, not a unit-file editor or a general package-configuration manager.

Advanced host tools

Docker and host operations, with the risk visible.

Docker is reached through the host's CLI over SSH — never a mounted socket. Containers can be inspected, logged, started, stopped, restarted or removed by validated ID. Package lifecycle and Drovik-managed cron tasks are enumerated and audited. Destructive storage and network commands are opt-in, administrator-only and require explicit confirmation.

  • Potentially root-equivalent. The UI says so. Docker actions are confirmed, authorized and audited.
  • Enumerated actions. Start, stop, restart and remove; no arbitrary Docker commands and no Compose or Kubernetes manager.
  • Destructive changes are opt-in. Mount/format/partition and interface/route/firewall actions stay disabled until the operator sets DROVIK_ENABLE_DESTRUCTIVE_HOST_OPS=true.
  • Typed confirmation. Format and partition require the exact device name; protected mountpoints and mounted devices are refused.
  • Read-only users are blocked. A read assignment cannot run a container or host action.

Snippets

Commands you can read before they run.

Save a named command template with optional variables. Values are shell-quoted, the substituted command is previewed, and the run is confirmed against a specific server. Snippets execute as your SSH user and are audited.

  • One substitution rule. Values are quoted for the shell; the preview shows exactly what will be sent.
  • Target confirmation. A snippet is always run against an explicitly selected server.
  • Not a secret store. The editor warns against storing credentials in a template; snippets are per-user, not shared.
  • Read-only accounts cannot run them. The backend checks write access before execution.

Access & audit

The permission model is the feature.

v1.1.0 added local users, three roles and per-server assignments. The backend enforces them on every server-scoped route, so a read-only account is not merely a hidden button.

  • Administrator, operator, read-only. Administrators manage users and servers; operators work within their assignments.
  • Read or write, per server. Owners and administrators retain write access. Read-only assignments block the terminal, file mutations, Docker actions, snippets and alert changes.
  • No lockout. At least one active administrator must remain, and a user cannot delete themselves.
  • Scoped audit. Logins, connections and sensitive actions are recorded as local metadata — not file contents or terminal output.

Honest limits

What Drovik still refuses to do.

These are not footnotes. They are the boundary that keeps the tool reviewable and its privilege model understandable.

  • Linux first. Linux gets the full feature set. macOS and BSD get read-only monitoring; Windows is not supported.
  • Destructive changes are opt-in. Disk, network and firewall actions are disabled by default, administrator-only and confirmed. A wrong command can still destroy data or cut the host off.
  • Identity is local or OIDC. Local MFA is available. OIDC links to a pre-existing account and never auto-provisions users. Vault can supply SSH credentials without storing them.
  • Alerting stops at webhooks. Threshold alerts stay in the app or go to an encrypted webhook; there is no email, chat or pager integration.
  • No resumable transfers or unit editing. Transfers stream; systemd actions are enumerated.
  • SQLite single-writer. Use local storage and stop Drovik for cold backups; forward-only migrations require a backup.

Real-host validation is bounded. Compatibility is checked against automated fixtures and a documented distribution matrix, not an exhaustive lab. Report gaps with the distribution, tool versions and the stable error code.

No false success still applies. A green button is not evidence. The result you see comes from the remote command, the SFTP result or a re-read of host state.
