Accessibility

Access is part of the interface.

Drovik is used for long, careful work. A control that only works with a mouse, or a status that is only conveyed by color, is a defect. This page describes the target, what is implemented, and the limits that remain honest.

1. Commitment

Drovik targets WCAG 2.2 Level AA for the marketing website and the core workspace flows. Accessibility is part of the project's definition of done: keyboard operation, visible focus, contrast, reduced motion and error states are reviewed with the feature, not added afterward.

This is a self-assessment, not an independent audit. The project does not claim full conformance, and a fork or a future change can regress it. The site itself is checked with automated tooling and a keyboard pass; the application's browser-level coverage is still growing.

2. What is implemented

  • Semantic structure. One main landmark per page, a skip link, ordered headings, labelled navigation and native controls where they fit.
  • Keyboard first. The theme switch, mobile menu, workspace tabs and copy buttons are reachable and operable by keyboard. Escape closes the mobile menu and returns focus to its trigger.
  • Visible focus. A high-contrast focus ring is never removed; it is designed to remain visible on both themes.
  • Contrast. Body text uses the ink palette's accessible steps, not the faintest label color. Status is carried by text and a dot, not color alone.
  • Reduced motion. The one entrance sequence, tab transitions and cursor blink are disabled or shortened under prefers-reduced-motion. Nothing autoplays media.
  • Reflow. The pages work down to 320px without horizontal page scrolling. Wide tables and code blocks scroll inside labelled regions instead of forcing the page sideways.
  • Content as text. Hostnames, filenames, process names, logs and terminal output are rendered as text, never trusted HTML. That also keeps them readable by assistive technology.
  • No-JS baseline. Navigation and content work without JavaScript. Controls that cannot function without it are hidden; the decorative preview falls back to its first panel.
  • Print. The policy pages print with chrome removed and external link URLs expanded.

3. The workspace

The terminal is a complex keyboard surface by nature. It is built on xterm.js, keeps focus visible, and is never the only way to perform a task: files, health, processes, services, logs and audit have their own labelled panels. The terminal still requires a screen reader strategy appropriate to terminal output; the project does not claim that a raw PTY is fully navigable in every screen reader.

Dense operational tables can require horizontal scrolling on a small screen. When they do, the scroll container is focusable and labelled. The visual mockups on this website are illustrative; their status text is real text, and the preview is captioned as synthetic data.

4. Known limits

  • Not independently audited. The target is WCAG 2.2 AA, the status is self-assessed, and automated tools cannot catch every barrier.
  • Terminal semantics. A full-screen PTY is not a standard document. Some screen-reader and voice-control workflows may be difficult, especially with rapidly changing output.
  • Charts and sparklines. Decorative charts are hidden from assistive technology where the same values are available as text. A chart that has no textual equivalent is a defect to report.
  • Third-party pages. GitHub, package registries and hosting providers are outside the project's control and have their own accessibility posture.
  • Browser coverage. Current Chrome, Firefox, Safari and Edge are supported. Legacy browsers and restricted embedded webviews are not part of the target.
  • No overlay. The project does not use an accessibility overlay or widget. Fixes belong in the markup and the component, not in a script that papers over them.

5. Feedback

If something is hard to see, reach or operate, open an issue at github.com/awbuilds/drovik and mention accessibility. Include the page or panel, the browser and assistive technology, what you expected and what happened. Do not include credentials, personal data or production hostnames.

For a security issue that happens to affect accessibility, use the private advisory route on the security page instead. Response is best-effort: Drovik is volunteer-maintained.

The standard is practical. A page that cannot be operated by keyboard is not “mostly accessible.” If a fix conflicts with the visual language, the interaction wins.
