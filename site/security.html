Security

A gateway needs a security argument.

Drovik holds credentials for machines that matter. The design assumes the browser is untrusted, the network is hostile and a remote host can lie. The controls are enforced in the Go service, not in the React UI.

01 / Boundary

The service is the only door.

The browser talks to one Go service over HTTPS and WebSocket. It never opens an SSH connection, never receives a stored SSH secret, and never chooses the address Drovik connects to. The service authenticates the session, authorizes the resource, decrypts a credential only at connection time, and runs a structured operation over SSH or SFTP.

02 / Controls

Controls that fail closed.

Every request passes through recovery, request identity, security headers, body limits, authentication, CSRF, authorization, validation, a bounded handler context and safe error mapping. The groups below are the parts that matter most.

Authentication
Argon2id password hashes with per-password salts and versioned encoding. Login responses are generic; failures are rate-limited by IP. First-run setup exists only while no administrator exists.
Sessions
Opaque 256-bit session tokens; only their SHA-256 hash is stored. Idle and absolute expiry are enforced server-side. Logout revokes the session, and password changes revoke the account's other sessions.
CSRF & origin
Cookie-authenticated mutations require a session-bound synchronizer token and an accepted Origin/Sec-Fetch-Site. SameSite=Lax is an additional layer, not the only one.
Secrets
SSH credentials use AES-256-GCM with a random nonce and associated data binding the record. The key comes from the environment or a mounted file, never from SQLite or the image. Decryption happens only immediately before a connection.
Authorization
Every server-scoped request is authorized in the backend. Local roles and per-server read/write assignments are enforced on the route, not in the sidebar. Read-only accounts cannot open a PTY or change remote state.
Remote operations
Structured operations only, with enumerated signals and service actions. The terminal and user-authored snippets are the only arbitrary-command paths. Paths are normalized and checked for traversal and symlink escapes.
Bounds
Timeouts, output sizes, upload limits, concurrent destinations, session counts and request bodies are bounded. A missing capability fails with a stable code rather than retrying indefinitely.
Egress
Loopback, link-local, multicast, unspecified, reserved and cloud metadata endpoints are denied by default. Public and RFC1918 targets are allowed by default for self-hosted use, with operator overrides; deny wins over allow.
Browser surface
The app uses a strict CSP and security headers, validates WebSocket authentication and origin, enforces message size and rate limits, and renders filenames, logs and terminal output as text — never raw HTML.
Logging
Structured logs carry a stable code, correlation ID and safe context. Authorization headers, cookies, passwords, keys, tokens, file contents, terminal I/O and log contents are redacted. There is no external telemetry.
Deployment
The supported container runs non-root on a distroless image with a read-only root filesystem, no Linux capabilities and no-new-privileges. The encryption key is a separate secret; port 8080 binds to loopback behind TLS.

03 / Host keys

A changed key stops the connection.

Host-key verification is strict and has no insecure fallback. The first connection is a deliberate decision; every later connection is a comparison.

04 / Authorization

Roles are enforced on the route.

Administrators manage users and servers. Operators work within their assignments. Read-only users can inspect assigned servers but cannot change remote state. Owners and administrators retain write access; the backend checks both the account role and the assignment.

The table is a product summary, not the full policy. Assignments, owner access and the last-administrator invariant are implemented in the backend.

05 / High-risk surfaces

Power that is named as power.

Docker

Docker access is reached through the host's CLI over SSH. Drovik never mounts a Docker socket into its own container. The interface exposes listed containers, images, logs and inspection, plus start, stop, restart and remove by a validated container ID. These actions are potentially root-equivalent; they require confirmation, are audited, and are blocked for read-only assignments. This is not a Compose or Kubernetes manager.

Snippets and the terminal

The terminal and user-authored snippets are arbitrary-command paths by design. Snippet values are shell-quoted, the substituted command is previewed, and a specific server must be confirmed before execution. Snippets run as the SSH user, never with hidden elevation. Access control is the security boundary — not a promise that a user-authored command is safe.

Destructive host operations

Mount, format, partition, interface, address, route and firewall actions are disabled by default. When an operator enables DROVIK_ENABLE_DESTRUCTIVE_HOST_OPS, they remain administrator-only, require CSRF and explicit confirmation, reject protected mountpoints and mounted devices, and are audited. Format and partition require typing the exact device. A wrong command can still destroy data or cut the host's connectivity; test on a disposable target.

Credentials and identity

SSH credentials are encrypted with AES-256-GCM unless an operator stores only a HashiCorp Vault KV v2 path; Vault secrets are fetched at connect time and never written to Drovik. Local TOTP secrets are encrypted and recovery codes are hashed. OIDC uses authorization-code + PKCE, checks the discovery issuer, and never auto-provisions or matches accounts by username: a signed-in user links an existing account explicitly.

Treat a Drovik administrator as privileged. The app can reach every server assigned to that account. Run it behind TLS, restrict who can reach it, and keep the encryption key and database backups separate.

06 / Audit record

Two runs, twelve fixes, no clean bill of health.

Two source-first audit runs were completed on 8 November 2026. The first covered the v1.0.0 tree and fixed five confirmed findings in v1.0.1. The second covered the Phase 9 tree at v1.1.0 and fixed seven confirmed findings in v1.3.1, plus additional hardening. Further validation leads were recorded with non-destructive reproduction plans; they were not confirmed vulnerabilities and were not assigned severity. The full report and evidence live outside the repository; the public summary is in the audit note.

v1.0.1 / first run

SeverityIssueFix
HighChanging authentication method could reinterpret a stored private key as a password.Method changes require a credential of the new type; stored secrets are never decrypted under a different method.
MediumTerminal PTYs survived logout, revocation and session expiry.Terminals are bound to the application session, closed on logout, and revalidated every 30 seconds.
MediumIPv6 zone identifiers bypassed the egress deny policy.Zone identifiers are rejected; loopback, link-local, multicast and unspecified checks are explicit.
MediumUploading over a 0600 file could widen it to the SFTP default mode.Staging is private; the final mode is applied before an atomic rename, and a failed chmod aborts.
MediumThe journal parser ignored the requested line count.Parsing stops at the requested count and marks the window truncated.

v1.3.1 / second run

SeverityIssueFix
MediumSnippet substitution could expand one request into gigabytes before the 64 KiB check.Bounded per-value limits, a running-budget builder and declaration validation.
MediumTwo administrators deactivating each other concurrently could leave zero active administrators.A statement-level post-state guard and explicit last-administrator conflict mapping.
LowCollector section assembly was quadratic in the remote line count.Linear builders with a per-section line cap.
LowA failed post-signal state read was reported as “not running” with a success audit.Explicit OUTCOME_UNKNOWN and an unknown audit outcome.
LowA delivered signal could lose its audit row when the request was canceled.A detached, bounded audit context.
LowNon-finite host load or uptime could be persisted and turn APIs into empty 200 responses.Finiteness checks, storage guards and marshal-before-write JSON.
LowConcurrent overview requests persisted duplicate metric samples.A unique (server_id, collected_at) index with ON CONFLICT DO NOTHING.

The second run also bounded alert-rule cardinality and identifier length, sanitized Docker inspect labels, added no-store to advanced responses, and pinned container base images by digest. The dependency review upgraded golang.org/x/crypto past GO-2026-5932 and reduced workflow token permissions.

The second run covered the Phase 9 tree; it was another source-first review, not an independent external audit. The advanced-management surfaces have their own threat-model decisions in ADR 0013 and are covered by tests. Report suspected issues privately; do not test them against systems you do not own.

07 / Reporting

Report privately. Do not open a public issue.

Use GitHub's private vulnerability reporting from the repository's Security tab. Include the affected version or commit, impact, reproduction steps and any suggested fix. Do not include real credentials, private keys, customer data or production hostnames in a report; use synthetic examples.

Expect acknowledgement within 7 days and an initial assessment within 14 days where feasible. This is a volunteer-maintained project: these are targets, not contractual SLAs. Coordinated disclosure follows a fix and a reasonable upgrade window.

In scope

  • Authentication, session, CSRF and authorization weaknesses.
  • Host-key verification bypass, credential exposure and secret leakage.
  • Command injection in structured operations; path traversal or symlink escape.
  • SSRF or egress-policy bypass; WebSocket origin or authentication bypass.
  • XSS through filenames, hostnames, process names, logs or terminal output.
  • Resource exhaustion that affects other users or the host.

Out of scope

Compromised administrator accounts, physical access, unsupported browsers, social engineering, single-user self-DoS that stays within documented limits, and automated scanner output without demonstrated impact.
