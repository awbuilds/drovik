Privacy Policy

What is stored, and where it stays.

Drovik is self-hosted software with no project-operated service, no account and no telemetry. This page describes the static website you are reading and the data a Drovik instance stores on the machine you control.

The short version

  • This website is static. It sets no cookies, runs no analytics and loads no third-party resources. A theme preference stays in your browser.
  • The Drovik application stores what it needs to operate on the machine you run it on: accounts, sessions, server records, encrypted credentials, host keys, audit metadata, snippets, assignments, configurable metric samples and alert rules.
  • The project maintainers do not receive instance data, cannot access your database and run no hosted Drovik service.
  • If you run an instance, you are the operator and controller of the data in it. Your backup, retention and access decisions are yours.
  • There is no telemetry, advertising, crash reporting or vendor cloud.

1. Scope

This policy covers two things: the static project website at the canonical URL on this site, and the Drovik software as published in the v1.3.0 release line. It does not cover a hosted service — the project does not operate one — or a modified fork, an operator's own policies, or third-party sites such as GitHub.

Drovik is free software under the GNU Affero General Public License v3.0 only. The license governs your rights to use, study, modify and redistribute the code. This policy describes data handling; it does not replace the license or the operator's own legal obligations.

2. This website

This site is a set of static HTML, CSS and JavaScript files. It has no account system, no forms, no comment system and no newsletter.

  • No cookies. The site sets none.
  • No analytics or advertising. There is no tracking script, pixel, fingerprinting script or third-party tag.
  • No third-party subresources. Fonts, styles, scripts, icons and images are served from this site. External links are ordinary links; they load nothing until you follow them.
  • Theme preference. If you use the light/dark switch, your choice is stored in your browser's localStorage under a site-specific key. It is never sent to the project or to a third party. Clearing site data removes it.
  • Hosting logs. A hosting provider may keep standard request logs — IP address, user agent, timestamp, requested path — under its own policy. The project does not receive, combine or analyze those logs. If you need details for the specific deployment, contact the operator of that deployment.

Following a link to GitHub, a package registry or another site leaves this site and is governed by that site's policy. The project does not control those services.

3. The software: what an instance stores

A self-hosted Drovik instance stores its operational data locally, normally in SQLite in the configured data directory. The table describes the data model shipped in v1.3.0; an operator can extend or modify a fork.

DataWhy it existsNotes
AccountsSign-in and role checksUsername, Argon2id password hash, role, active flag, timestamps, last login. No plaintext password is stored.
SessionsKeep you signed inOpaque token hash, user reference, user-agent string, created/last-seen/expiry times, revocation time.
ServersSaved connectionsDisplay name, host, port, username, auth method, encrypted credential and nonce, optional encrypted passphrase, tags, notes and timestamps. Credentials are never returned to the browser after submission.
Known hostsStrict host-key trustHost, port, key type, fingerprint, public key, approval metadata and revocation time.
CapabilitiesShow available host toolsSafe detection metadata such as which commands and service manager were found.
Audit eventsOperational historyActor and server references, event type, target summary, outcome, stable error code, correlation ID and timestamp. Not file contents, terminal I/O or log contents.
SnippetsSaved command templatesName, description, command template, variable definitions and owner. The editor warns against storing secrets.
AssignmentsPer-server accessUser, server and read/write access level.
Metric samplesLocal history and alertsNumeric host metrics and timestamps, retained for a configured window with a hard sample cap. Configurable retention; not sent anywhere.
Alert rulesIn-app thresholdsMetric, comparator, threshold and enabled state. No external notification destination is stored.
SettingsInstance configurationOperator-controlled application settings stored in the local database.

What is not stored by default: plaintext SSH passwords or private keys, plaintext session tokens, the encryption key, remote file contents, terminal input or output, or journal/log contents. File transfers stream through the service; an upload uses a private staging file on the target host for an atomic write, and Drovik does not keep a local copy. Metrics snapshots are cached in memory; only sampled values are persisted when local history is in use.

The managed host receives the operations you run and may keep its own logs — SSH authentication, shell history, systemd journal, Docker logs, file changes. Those are outside Drovik and governed by the host's configuration and the operator's policy.

4. No telemetry or third-party processing

Drovik does not contain analytics, advertising, crash-reporting or update-check code that contacts the project or a vendor. It makes no request for usage data or diagnostics. The service's only outbound connections are to the SSH hosts you configure and operate. The website makes no third-party request at all. Any reverse proxy, backup storage or identity service you add is part of your deployment, not a call made by Drovik.

If a future feature introduces optional telemetry, it must be opt-in, documented and free of secrets. That is the project's rule, and it is not implemented today.

5. Who is responsible

The project maintainers publish the software and this static site. They do not operate a Drovik instance for you, do not have a copy of your database and cannot access your credentials, audit history or server data.

If you run Drovik, you are the operator and the controller of the instance data. That includes deciding who gets an account, what they can reach, how long audit and metric data is kept, how backups are protected and how you respond to access or deletion requests. If you use someone else's instance, that operator is the right contact — not the project.

6. Your rights

The project does not process personal data about you through this website beyond the local theme preference and whatever a hosting provider independently logs. It therefore has no instance data to access, correct, export or delete on your behalf.

If you are in the EEA, UK, California or another region with data-protection rights, those rights apply to the operator of the instance that holds your data. The operator can use the local database, the administrator UI and backups to respond. The software provides account creation, role management, password reset and account deletion; audit events are metadata and may remain after an account is deleted, with the actor reference cleared. The project cannot compel an operator to change their retention or access practices.

7. Retention and deletion

  • Sessions end at idle or absolute expiry, on logout, on password reset or when an account is disabled. The session row can remain as a revoked record until the operator cleans it up.
  • Audit events are retained until the operator removes them. Drovik does not silently expire audit history, and the local database is not claimed to be tamper-proof.
  • Metric samples are bounded by the configured retention window and sample cap. Lowering either prunes older samples.
  • Snippets, assignments and alert rules remain until changed or deleted, or until the related account or server is removed.
  • Accounts and servers can be deleted by an administrator. Deleting an account removes its sessions; server records owned by that account are removed by the database's ownership constraint. Audit events can remain as unlinked metadata.
  • Federated identity and external secrets store only the OIDC issuer/subject on the local account and, for Vault-backed servers, the Vault path. MFA secrets and webhook URLs are encrypted. The identity provider and Vault are operated by you and have their own data policies.
  • Everything at once is the data directory and database, plus any backups. Deleting them removes the instance's local data. Backups and the encryption key are separate and must be handled deliberately.

If the encryption key is lost, stored SSH credentials cannot be recovered. That is a security property, not a support gap.

8. Security

Passwords are hashed with Argon2id. SSH credentials are encrypted with AES-256-GCM and a key kept outside the database. Session tokens are stored only as hashes. Authorization is enforced in the backend, and read-only assignments block mutation paths. Terminal and SFTP sessions are bounded and cleaned up.

No software is perfectly secure. The operator is responsible for TLS, network exposure, administrator access, backups and the security of the machine running Drovik. See the security page for the full model and the private reporting route.

9. Third parties

This website links to GitHub for source, releases, issues, discussions and security advisories. GitHub processes data under its own privacy statement. The project may also link to package registries or standards bodies; those sites have their own policies. There are no embedded third-party frames, fonts, scripts or analytics on this site.

A Drovik deployment may use a reverse proxy, container registry, identity provider or backup storage chosen by its operator. Those services are part of the operator's deployment, not the project's.

10. Children

Drovik is infrastructure software for managing Linux servers. It is not directed to children under 16, and the project does not knowingly collect information from them. An operator who makes an instance available to others is responsible for setting an appropriate minimum age and access policy.

11. Changes

This policy is updated when the software's data handling changes. The effective date at the top moves, and the change is visible in the project's public history and release notes. A modified fork may handle data differently; this policy describes the published Drovik release line, not every fork.

12. Contact

For a privacy question about this website or the published software, open a minimal GitHub issue or discussion at github.com/awbuilds/drovik. Do not include personal data, credentials or instance data in a public issue. For a security concern, use the repository's private advisory flow described in the security policy.

For a question about data in a specific Drovik instance, contact that instance's operator. The project cannot access it.

This page is a good-faith description of the published software and website. It is not legal advice; operators should obtain their own advice for their jurisdiction and deployment.
