Install

One service. No agent on the other end.

Drovik is a single Go service with an embedded SQLite database and a separately mounted encryption key. The supported path is a container behind TLS. This page takes you from clone to first-run setup, then through backup, upgrade and verification.

01 / Requirements

What must already be true.

Drovik does not install anything on the servers it manages. It needs an SSH account, the host's standard Linux tools, and a browser that can hold a WebSocket.

Controller
Linux amd64 or arm64 for the container image or release archive. Docker Engine with the Compose plugin for the primary path. Go 1.27+, Node 22+ and pnpm 12 for a source build.
Managed host
Linux with /proc and OpenSSH 7.4+ (or compatible). The SFTP subsystem is required for Files. systemd 230+ with systemctl is required for Services; journalctl with JSON output for Logs; ps with -eo (procps-ng preferred) for Processes.
Browser
A current Chrome, Firefox, Safari or Edge with ES2022, WebSocket and ResizeObserver support. The workspace is not supported on legacy browsers.
Network
A TLS reverse proxy in front of 127.0.0.1:8080 for any non-local deployment. WebSocket upgrade support and long read timeouts are required for terminal sessions and large transfers.
Secrets
One 32-byte encryption key, supplied as base64 or a file. It must not live in the database, the image or the repository. Losing it makes stored SSH credentials unrecoverable.

02 / Docker Compose

The primary path: four steps.

The Compose example binds the service to 127.0.0.1:8080 and expects a reverse proxy to terminate TLS. It runs as a non-root user on a distroless image with a read-only root filesystem, no Linux capabilities and no-new-privileges.

01

Clone and create the environment file

deploy/compose 
git clone https://github.com/awbuilds/drovik.git
cd drovik/deploy/compose
cp .env.example .env

Edit .env and set DROVIK_PUBLIC_URL and DROVIK_TRUSTED_ORIGINS to the exact HTTPS origin users will open. Keep the file out of version control.

02

Generate the encryption key once

deploy/compose/secrets 
mkdir -p secrets
openssl rand -base64 32 > secrets/encryption.key
chmod 600 secrets/encryption.key

Back the key up separately from the database. The container receives it as a Compose secret, not as an environment value or a file inside the data volume.

03

Start the service

deploy/compose 
docker compose up -d --build
docker compose ps

For a released image, set DROVIK_IMAGE in .env to the release tag and use docker compose up -d. Pin a tag in production; do not float on latest.

04

Put TLS in front, then finish setup

Do not expose the raw port. Configure the reverse proxy, open the public HTTPS URL, and complete first-run setup before untrusted users can reach it.

Setup is claimable. Until the first administrator exists, whoever can reach the setup page can create it. The route is rate-limited, but that is not a substitute for network control.

03 / Reverse proxy

Terminate TLS, forward WebSocket.

The repository includes a Caddyfile and an Nginx server block. Use them as the starting point; they add HSTS, nosniff, a referrer policy, a 2 GB request body limit and the long read timeouts terminal sessions need.

Caddyfile — minimal shape 
drovik.example.com {
  encode zstd gzip
  reverse_proxy 127.0.0.1:8080 {
    header_up X-Real-IP {remote_host}
    header_up X-Forwarded-Proto {scheme}
  }
}

Use the full Caddyfile or Nginx example. Nginx needs proxy_http_version 1.1, the upgrade headers and long proxy timeouts.

Keep the container bound to loopback or a private interface. If the proxy and Drovik are on different hosts, bind the service to a private address and firewall it to the proxy only.

04 / Source build

Build both halves, then run the service.

The release archive bundles the built frontend. A source build produces the same pair: the Go binary serves the Vite output from DROVIK_STATIC_DIR.

source build 
git clone https://github.com/awbuilds/drovik.git
cd drovik/frontend
pnpm install --frozen-lockfile
pnpm build
cd ../backend
go build -o drovik ./cmd/drovik

Create a production environment file and key following the local setup guide. Run the binary from backend/ so the default ../frontend/dist static path and the relative data/key paths resolve as documented. Native packaging is secondary to the container path for the MVP; a hardened systemd unit template is in the repository.

05 / Releases & systemd

Use an artifact built by CI.

Tagged releases publish Linux archives and a container image built from the tagged commit. The release workflow attaches SHA256SUMS and generates release notes. Verify a download against the checksum before running it.

  • drovik-v<version>-linux-amd64.tar.gz and ...-linux-arm64.tar.gz — binary plus the built frontend.
  • ghcr.io/awbuilds/drovik:<version> — the container image; stable releases also update latest.
  • SHA256SUMS — verify the archive before extracting it.

Browse releases · systemd unit template

verify a release archive 
sha256sum -c SHA256SUMS --ignore-missing
tar -xzf drovik-v1.1.1-linux-amd64.tar.gz

The exact archive name follows the tag. Replace the version if you are installing a different release.

06 / First-run setup

Create the first administrator deliberately.

Open the public HTTPS URL. If no administrator exists, Drovik serves the setup route. Create the first account, then sign in. Setup is disabled after the first administrator exists and is rate-limited per IP, but the network boundary is still yours to set.

After setup, add a server, test the connection, and review the host-key fingerprint before the first real session. The setup flow does not install anything on the managed host.

Do not leave a fresh instance on the public internet. Reach it through a private network or tunnel until setup is complete. After setup, restrict who can reach the login page and use a strong administrator password.

07 / Backup & upgrade

The database and the key are one backup.

A complete backup needs the SQLite database from the drovik-data volume and the encryption key. Back up consistently — stop the container or use SQLite's backup API — encrypt the backup, and store the key separately. If the key is lost, stored SSH credentials cannot be recovered.

cold backup — deploy/compose 
docker compose stop drovik
docker run --rm -v drovik_drovik-data:/data -v "$PWD/backups:/backup" alpine \
  tar -czf /backup/drovik-data-$(date +%Y%m%d).tar.gz -C /data .
docker compose start drovik

To upgrade: back up the database and key, pull or build the new version, start it, and let migrations run before the service accepts traffic. Verify /readyz and the version in Settings. A failed migration is a failed upgrade; restore the backup rather than serving a half-migrated database. Migrations are forward-only.

08 / Verify

Three checks after every start.

Drovik exposes two health endpoints and a version endpoint. They do not disclose secrets, host lists or internal paths.

EndpointWhat it proves
GET /healthzThe process is alive.
GET /readyzConfiguration and database are ready to serve.
GET /api/v1/versionBuild and version metadata; no secrets.

Also open Settings in the app and confirm the version on the running instance. If /readyz fails after an upgrade, treat the upgrade as failed and restore the documented backup.

09 / Troubleshooting

When the host says no.

Most failures are remote capability or permission issues, not Drovik bugs. Start with the stable error code in the UI and the compatibility matrix.

  • SSH_HOST_KEY_UNKNOWN / SSH_HOST_KEY_CHANGED: review the fingerprint. A changed key is a stop sign, not a prompt to click through.
  • SFTP_PERMISSION_DENIED: the SSH user cannot read or write that path. Drovik does not escalate.
  • CAPABILITY_UNAVAILABLE: the host lacks the tool or service manager for that panel. The compatibility page lists what is required.
  • OUTCOME_UNKNOWN: the remote result could not be confirmed. Re-read the state before retrying a mutation.

Before you expose it

TLS, a strong administrator password, and a backup outside the volume.
